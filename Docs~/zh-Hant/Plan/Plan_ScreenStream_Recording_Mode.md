# ScreenStream 錄播模式

> 一句話：**直播是 ring（會繞回去覆寫），錄播是流（不繞、不覆寫）—— 兩條各自單純，不要互相遷就。**

## 0. 這份文件怎麼來的

2026-08-01 晚間，Tim ↔ basecamp ↔ kaguya ↔ apex-one 在酒館討論收斂而成。
起點是 kaguya 的提案「把觀影工具擴充成可重播分析」（seq 14324），中途 Tim 連續修正了四次方向，
**每一次修正都讓設計更簡單**。本文記錄的是**最終形狀 + 每個決定為什麼是這樣**（理由比結論值錢，
因為之後有人想改的時候，需要知道當初排除了什麼）。

---

## 1. 需求

看直播時可以「開錄」，把這一段完整留下來，之後沒有時間壓力地慢慢看 —— 可以慢速播放、甚至逐張看。

現況做不到：ring buffer 只有 `max_frames` 個槽位（現設 2400 = 40 分鐘 @1fps），滿了就繞回去覆寫。

---

## 2. 核心決定與理由

### 2.1 錄播無視 `max_frames`，寫進獨立資料夾

**改動面極小 —— `max_frames` 全專案只有一個消費點：**

```python
# screenstream_daemon.py:718
frame_idx = (cfg["frame_count"] % cfg["max_frames"]) + 1   # ← 錄播模式下不取 mod
```

C# 端完全沒有邏輯依賴它（只有 `UCL_ScreenStreamPage` 讀寫該欄位的 UI + 一行註解）。

**必須用獨立資料夾**，理由是硬的：錄播的 index 從 1 開始遞增，會**直接撞上 ring 的槽位 1,2,3…**，
兩邊互相覆蓋。所以錄播走 `_screenstream/<錄製資料夾>/`。

> ⚠ **待 Tim 拍板**：錄播期間 ring 要不要繼續滾？
> - **(A) 暫停 ring**：最單純，但陪看的 montage 沒有新幀可讀（除非它也能指向錄播資料夾）。
> - **(B) 雙寫**：陪看完全不受影響，代價是雙倍寫入（68 KB/幀，一集 24 分才 90 MB，不痛）。
>
> 這題決定「錄播的時候還能不能同時陪看」。

### 2.2 檔名沿用 `frame_NNNNNN`（index），不用相對時間戳

中途曾決定過「檔名 = 相對經過時間」（`000350_000.jpg`），後由 Tim 改回 index，理由是
**工具讀取最直接（index ÷ fps 就是時間）+ 相容現有直播格式，盡量共用框架**。

> 📌 **一條血證的正確適用範圍**：skill 裡有「ring buffer 檔名 index ≠ 時間序」這條血證，
> 一度被拿來反對本方案 —— 那是**誤用**。該血證的前提是「會繞回去覆寫」；
> 錄播不輪替、從 1 單調遞增、永不 wrap → **前提消失，結論不成立**，index 在這裡就是時間序。
> **規則要連著它的前提一起搬，不能只搬結論。**

### 2.3 寬度 `:04d` → `:06d`（必須，不是建議）

`:04d` 是**最小寬度、不截斷**，所以不會崩，會安靜地變長 —— 然後字典序在跨位數時崩掉：

```
sorted → frame_0999, frame_1000, frame_10000, frame_9999
                                  ↑ 10000 排到 9999 前面
```

錄播沒有 wrap，index 在 **2.8 小時**（@1fps）就衝破 9999。
6 位數 @1fps 撐 **11.6 天**、@2fps 撐 5.8 天。

**施工**：改寬度會讓舊的 `frame_0001` 與新的 `frame_000001` 混在同一資料夾 →
**改格式時直接清空 `frames/`**（ring buffer 本來就是 ephemeral，清掉零損失）。

### 2.4 index = 寫入序號，且**嚴格不跳號**

曾討論過「時槽序號（掉幀留洞，index/fps 恆準）」vs「寫入序號（連續無洞，掉幀會累積漂移）」。
**Tim 拍板寫入序號 + 嚴格避免跳號**，理由是：

> 觀看錄播沒有時間壓力，可以慢速播放甚至逐張觀看。

也就是說 —— **錄播的 index 是「播放軸」，不是「牆鐘測量」。**
逐張看時缺號是真的麻煩（人跟工具都要處理不存在的檔）；而某一幀究竟是第 500.0 秒還 501.2 秒拍的，
沒有人在乎。**連續性 > 牆鐘精度**，對這個用途是對的取捨。

**實作要求（必寫進註解，否則會被下一個人善意改掉）**：
- index 只在**寫檔成功後**配發；失敗用同一個號重試，**絕不前進**
- 單一配號者，不並行配號

**牆鐘軸零成本另外有**：檔案 mtime 就是。所以
- **播放軸** = `frame_NNNNNN` 的 index（連續、不跳號）→ 播放 / 跳段 / 逐張
- **牆鐘軸** = 檔案 mtime → 對齊 STT / OCR（那兩者是牆鐘戳的：`stt_<epoch>.json`）

manifest 記 `started_at` + `fps` + 實際結束牆鐘 → **兩者一比，漂移就是可觀測的數字**，
而不是慢慢歪掉的字幕。

### 2.5 停錄 = rename，不是 copy

```
① 停止錄製（daemon 不再寫該資料夾）
② rename <固定名稱> → <錄製名稱>
③ mkdir 回原本的固定名稱（空的，manifest 一併重置、index 從 1 重來）
```

**這一招把整段「匯出」的複雜度消滅掉了。** 同磁碟 rename 是 O(1) metadata 操作，
2400 張圖一張都不用搬 —— 先前討論過的「匯出時的讀寫競爭 / 88:1 吞吐比 / 提前觸發的安全餘裕」
**全部作廢**：沒有複製，就沒有競爭。

附帶好處：
- daemon 永遠寫同一個固定路徑，不必執行期換路徑、不必事先知道錄製名稱
- **ffmpeg 變成可選** —— 資料夾本身就是成品，編碼成影片是之後獨立一步
  （本機目前 PATH 上沒有 ffmpeg，MVP 不被它卡住）

> ⚠ **Windows 順序坑**：目錄內有開啟中的檔案 handle 時 rename 會被拒（sharing violation）。
> 所以②**必須**在 daemon 停寫之後；而且**②失敗就不能走③** ——
> 否則舊資料夾留著、新的又建不出來，下一段錄影會接在舊的後面，index 還會撞。

**錄製名稱可事後再取**：停錄當下未必知道在看什麼 → 預設用時間戳當資料夾名。
之後手動改名不影響任何機制，因為**沒有任何 code 依賴資料夾名稱**（真相在 manifest）。

### 2.6 錄影長度上限 = 一種「結束」

沿用 Tim 的「中斷視同錄製結束」原則。若之後仍保留容量上限語意，
**達到上限就自動判定錄影結束（並觸發輸出/改名），但直播不中斷**。

好處是**永遠不會產出半截壞掉的東西** —— 錄出來的每一段都是完整連續的，只是有長度上限。

## 3. manifest

每個錄製資料夾一份。**錄的時候寫「事實」**（這段錄了什麼），跟播放時產生的 report
（該次取樣的描述）是兩份不同東西，不要合併。

| 欄位 | 為什麼 |
|---|---|
| `status` | `recording` / `complete` / `interrupted` ← 見下方狀態機 |
| `started_at` / `stopped_at` | 絕對時間唯一的落點 |
| `fps` | index→時間換算的分母；**全段不可變**（見下） |
| `frame_count` / `last_index` | 對帳：檔案數 vs 宣稱數不符 = 有東西被刪或沒寫完 |
| `ocr_enabled` / `stt_enabled` | **錄製當下**的值。事後沒字幕要分得出「當時沒開」還是「開了但辨識失敗」 |
| `monitor` / 解析度 | 換螢幕會讓裁切位置全變 |
| `title` | 片名，可留空事後補 |

### 3.1 狀態機 —— 中斷也要留下痕跡

「中斷視同結束」預設了**結束時有人寫得下 `stopped_at`**。
而中斷最常見的形態（daemon 被砍 / Editor 崩 / 斷電）**沒有任何 code 跑得到那一行**。

```
開錄        → 立刻寫 { status: "recording", started_at, fps, ... }
正常收播    → status: "complete" + stopped_at + frame_count
daemon 啟動 → 掃錄製區：任何 status 仍是 "recording" 的
              → 改 "interrupted"，stopped_at = started_at + last_index/fps
```

最後一行剛好被 index 設計吃下來：**最後一幀的 index 就是它的相對結束時間**，一行減法。
→ **不需要中斷當下有機會執行任何東西。**

### 3.2 fps 中途變更 = 視同中斷、開新資料夾

換算的分母就是 fps。中途改 → **每一個推算出來的時間都是錯的**，
而 manifest 只有一個 `fps` 欄位、對應兩種間距，那欄位就開始說謊。

## 4. 磁碟成本（實測 68 KB/幀）

| | 幀數 | 大小 |
|---|---|---|
| 一集 24 分 | 1,440 | **0.09 GB** |
| 一部電影 2h | 7,200 | 0.47 GB |
| 一整天 12h | 43,200 | 2.8 GB |

@1fps ≈ **245 MB/小時**。無上限成長 → 需要一個低磁碟警告或手動停止，不必做複雜。
