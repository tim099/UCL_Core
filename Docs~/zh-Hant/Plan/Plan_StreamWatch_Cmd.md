# 觀影模式重做 — Spec

## 0. 一句話（Tim 2026-08-15 拍板）

觀影照自由時間的手法收進**專用 Cmd 分步**：`start` 註冊看到幾點並鎖定媒材身分，
之後每輪跑 `cycle` 取素材、跑 `observe` 發評論並記帳；**時間到或 Tim 停錄影時，
由下一次 `cycle` 判定並提示收工**。評論與心得**由 Cmd 自己發到酒館**，不再另外呼叫發文 Cmd；
**每一步的回傳檔都明示下一步**。計酬整合進流程，**session／時間／錢／通知四件在 C#**。

> ⚠ **本案是打掉重做，不是改寫。** 舊的 `stream_watch_session.py`（911 行）是 prototype，
> 新設計以**使用心得**為依據重新長出來 —— 因此**不做逐行對照**（Tim 2026-08-15 拍板）。
> 刻意不做的項目集中列在 §11，**每一項都有名字**：三個月後要分得出「漏了」與「決定不做」。

---

## 1. 這個活動實際上在做什麼

ScreenStream daemon 每秒寫一張 frame 進 ring buffer。agent 一輪（取材＋讀圖＋寫評論）要花數十秒，
**不可能一秒看一張去追 1 fps**。所以：

> **「跟上播放速度」≠「逐幀全解析度看」** —— 用縮圖牆做時間壓縮 ＋ cursor 接續，
> 把「跟上」跟「逐幀」解耦。

兩種失效：
- **gap（漏看）**：本輪窗口沒接上上輪尾巴 —— 畫面還在，可補
- **overflow（遺失）**：落後超過保存期 —— 舊幀被覆寫，**永久救不回**

---

## 2. 核心設計判斷

### 2.1 「自動」是**判斷自動**，不是**觸發自動**

Tim 的原話是「時間到會自動通知結束而不用另外判斷」。

⚠ **初版誤讀成「非同步推送」**，於是設計了酒保 daemon 的 deadline sweep、
再替它寫可靠度限制、再補第二觸發者 —— **在一格誤讀上蓋了三層樓**。

**正解**：跟自由時間一樣 —— **超時後，下一次觸發 Cmd 時由 Cmd 判定並通知**。
自動化的是「agent 不必自己算時間」，不是「不必呼叫」。

⇒ **不新增任何常駐偵測**；酒保 tick 一行都不必動。

### 2.2 agent 不能自己結束 session

**沒有 `step=end`。** 兩個終止條件都由 Cmd 判定：

| 終止 | 判定依據 |
|---|---|
| 到期 | `now >= ends_at` |
| Tim 中斷 | `_screenstream/_config.json` 的 **`enabled` 轉 false** |

⚠ **中斷只認 `enabled` 這個顯式欄位，不推論 frame 新鮮度。**
2026-08-15 實測活樣本：`enabled:false` 而 **994 張 frame 仍在磁碟上** ——
「錄影停了」與「frame 沒變新」是兩件事；用後者推論，daemon 打嗝／暫停都會被讀成中斷，
而 **session 誤殺加結算已發生、收不回**。

> 拿掉 `end` 入口的附帶價值：**「提早收工」是本專案 agent 病歷最厚的一族**
> （w40–w45 連續六次，形狀是「我交付完了」，最難抓因為它看起來像盡責）。
> **拿掉入口比要求記得別提早有效** —— 規則長在通道上，不掛在記憶裡。

### 2.3 四件搬 C#，不是「主架構搬 C#」

| 職責 | 落點 | 理由 |
|---|---|---|
| session／到期時刻／狀態機 | **C#（唯一寫入端）** | 與自由時間同契約，避免兩端各寫一份 |
| 到期／中斷判定 ＋ 通知 | **C#** | 判定與宣告同源 |
| 計酬結算 | **C#**，走 `UCL_TreasuryLedger` | 現行經 python 直寫是**繞過收銀台的旁路** |
| 評論／心得發文 | **C#（in-process post）** | 見 §5 —— 合併掉一條靠自律的規則 |
| **縮圖牆合成** | **python 工具，但由 Cmd 派工** | 不移植成 C#（影像處理沒有理由重寫）；
  由 `cycle` spawn 並回報產物路徑 —— **成本已量、有界**（§3.2） |
| **看圖 ＋ 寫評論** | **agent 本人** | 感知與判斷，沒有搬的餘地 |

⚠ 正名的理由：講「主架構搬 C#」會讓人以為縮圖牆也搬了。**四件，不多不少。**

## 3. Cmd 介面

```
run_cmd.py run StreamWatch --arg step=start   --arg persona=<P> --arg until=<HH:mm> [--arg media=<work>]
run_cmd.py run StreamWatch --arg step=join    --arg persona=<P>
run_cmd.py run StreamWatch --arg step=cycle   --arg persona=<P>
run_cmd.py run StreamWatch --arg step=observe --arg persona=<P> --arg-file body=<評論>
run_cmd.py run StreamWatch --arg step=note    --arg persona=<P> --arg-file body=<接續點>
```

| step | 做什麼 |
|---|---|
| `start` | 主觀影者：解析並鎖定 `media_id`（§4）→ 註冊 `ends_at` → 開播公告（記 `start_seq`） |
| `join` | 陪同觀眾：**繼承** primary 的 `media_id`，並取回至今評論摘要＋酒館游標（追上劇情） |
| `cycle` | **自己跑縮圖牆合成**（§3.2）→ 回傳圖／字幕／剩餘時間；**到期與中斷判定在此**；`## next` 狀態相依 |
| `observe` | **先發文、後記帳**；frame 數取自 `cycle` 當下記進 session 的值（agent 不傳數字也不傳路徑） |
| `note` | 寫接續點 → **自己發文** |

### 3.1 每步回傳檔的 `## next` 必須狀態相依

照早晚安流程的母版：**每步回傳檔指下一步的具體指令**，agent 不必背。

| session 狀態 | `## next` |
|---|---|
| 進行中 | 「繼續：跑 `step=cycle`」＋剩餘時間 |
| **到期／`enabled:false`** | 「**收工**：先跑 `step=note` 寫接續點，再跑 `cycle` 完成結算」 |
| 接續點已寫、待結算 | 「跑 `cycle` 完成結算」 |

⚠ **不可以是靜態文字。** 靜態的話「時間到了」會退回由 agent 讀剩餘分鐘自己判斷 ——
那正是本案要拿掉的那一格。

---

### 3.2 `cycle` 自己跑縮圖牆 —— 整合進 Cmd，不是回一句指令叫 agent 去跑

Tim 2026-08-15：**讀字幕、畫面等流程盡量整合到 Cmd，且詳細給予路徑與指令細節。**

⇒ `cycle` **自己 spawn 縮圖牆工具**，走 `UCL_ProcessRegistryService` 註冊 ＋ timeout，
把產物路徑直接寫進回傳檔。**agent 不組路徑、不抄數字。**

> ⛔ **不可以照抄 `UCL_BartenderDaemon.RunBalanceQuery`。**（初版寫「與它同形」——錯的。）
> 那支是**同步阻塞**：`out string err` 讓它不可能 async，內部 `while + WaitForExit(pollStepMs)`
> 是在主執行緒輪詢（2026-07-26 那次改動加的是**可取消與可視化，不是非阻塞**）。
> ⇒ 照抄它的形狀 ＝ **自動繼承它的同步性**。

**要抄的是 2026-08-03 全面 async 化那次的形狀**（Tim 指示；`WorkMemory/unitask-editor-async/`）：

| 要點 | 作法 | 反例／血證 |
|---|---|---|
| 阻塞的外部 process | `await Task.Run(() => proc.WaitForExit(...))` — 參考 `UCL_RemotePersonaLocator.RunScript:409` | CPU/IO 重活丟 thread pool，await 回來自動落主執行緒 |
| **`out` 參數會消失** | `bool F(out string err)` → `async UniTask<(bool ok, string err)>` | 呼叫端漏接 tuple 的 `err` **就是靜默失敗**（`RefreshLocatePreview` 實踩）⇒ 失敗必須落到 log |
| 防重入 guard | 旗標在 async 方法內 set／`finally` reset | ❌ `try { X().Forget(); } finally { flag=false; }` —— Forget 立刻返回，**旗標同幀放掉等於沒鎖**（2026-08-03 實踩） |
| 等待 | `await UniTask.Delay(...)` | ❌ `Thread.Sleep`（卡主執行緒） |

**可行性是量出來的**（2026-08-15 實測，`--after-mtime` ＋ `--max-tiles`，即真實 loop 路徑）：

| 回溯窗口 | 格數上限 | 耗時 |
|---|---|---|
| 60 s | 12 | **0.39 s** |
| 300 s | 12 | 0.46 s |
| 900 s | 12 | 0.57 s |
| **2400 s（滿保存期）** | 16 | **0.61 s** |

其中 **python 進程啟動＋import ≈ 0.064 s** 是每輪的固定成本（實測；短窗口時佔比最大）。

⇒ **成本與窗口跨度幾乎無關**（≈0.4–0.6 s）：格數封頂、stride 自動調整，
**圖的大小恆定 ⇒ 合成成本恆定 ⇒ 讀圖成本也恆定**。

⚠ **但「耗時 0.4 s」與「不會卡」是兩個問題** —— 它們只有在**非阻塞**時才等價。
初版拿耗時去回答「會不會卡」，而當時指定的實作形狀是同步的 ⇒ 那 0.4 秒就是 0.4 秒的凍結。
**走上面的 UniTask 形狀之後，這個數字才真的只是「多久拿得到圖」。**

> 🩸 **本節的初版是錯的，留著當紀錄。** 初版寫「線性、12 ms/frame、滿保存期外推 29 秒」，
> 並據此設計了「單輪窗口上限＋backlog 分批追」一整套機制。
> 那組數字量的是 `--last` 路徑 —— **而 `--max-tiles` 在該路徑下被靜默忽略**
> （帶 `--max-tiles 12` 仍渲染 900 格，無警告）。真實 loop 走 `--after-mtime`，格數確實封頂。
> ⇒ **我量了一個不會發生的工作量，然後替它設計了防禦。** Tim 指出「一輪大約讀 12–16 張、
> 不是每 frame 都讀」才翻出來 —— 而徵兆就在我第一次量測的輸出裡（我帶了 `--max-tiles 12`，
> 它印 `60 tiles`），我讀過去了。

⚠ **真正的取捨不在時間，在資訊密度**：2400 秒壓進 16 格 ＝ **一格涵蓋 2.5 分鐘**。
落後越多，**丟的不是時間、是細節** —— 每一格代表的時間變長，中間發生什麼看不見。
⇒ 所以間隔紀律仍然要有，但它的理由是**看得清不清楚**，不是**跑得快不快**。
⇒ `cycle` 回傳檔必須回報**每格涵蓋秒數**（`窗口秒數 ÷ 格數`），讓「我現在看得多粗」變成讀數而不是感覺。

⚠ 另一個獨立於本案的發現，**應另案處理**：`--max-tiles` 在 `--last` 路徑是 **no-op 且無警告**。
接受一個參數卻不套用，跟「沒有這個參數」在使用者眼裡同形。

### 3.3 `cycle` 回傳檔必須給完整路徑（不給片段、不給模板）

回傳檔至少要包含 —— **每一項都是可以直接 Read／直接執行的完整值**：

```
## 本輪素材
- 縮圖牆   : <絕對路徑>/_montage_<persona>.jpg      ← 直接 Read
- 字幕     : <絕對路徑>/_montage_<persona>.subtitles.md   ← 直接 Read（無則明寫「本輪無字幕」）
- 涵蓋     : 22:27:41 → 22:41:33（833s / 12 格，**每格 ≈69s**）  ← 每格秒數必列
- 積欠     : 0 frames（>0 時寫明並提示縮短間隔）
- 保存期   : 2400s（讀自 _screenstream/_config.json，不寫死）
- 剩餘     : 18 分鐘（到 14:30）

## next
1. Read 上面兩個路徑
2. 跑 step=observe --arg persona=<P> --arg-file body=<你的評論>
3. 之後再跑 step=cycle
```

⚠ **字幕沒有時要明寫「本輪無字幕」，不可以省略那一行** ——
省略之後「沒有字幕」與「這個欄位不存在」在讀者眼裡同形。（`empty-is-a-question`）

## 4. `media_id` 是共享鍵，不是各自命名

**由 primary 在 `start` 解析並寫進 session**，解析順序：

1. **先查既有 work** → 命中就用它
2. 沒命中才建新的，且**回報「這是新 work」**讓人有機會喊停
3. **片名不確定 ⇒ blocked，問 Tim** —— 憑印象取 slug 正是製造分裂的那一步

companion 走 `join` **繼承**，不自己解析。**一場一個鍵，而那個鍵有唯一的來源。**

> 🩸 活證據：`Library/works/princess-mononoke` ＋ `media/film-princess-mononoke/readers/`
> 已有 **Sirius／basecamp／summit 三個 reader**。若有人開場自己取名 `stream-mononoke-hime`，
> 同一部片會裂成兩個 work，**那三個人的既有心得對新場次永遠隱形 —— 而不會有錯誤訊息。**

### 4.1 媒材前綴認作品，不認收看方式

直播看《魔法公主》仍是 `film-princess-mononoke`，**不是** `stream-*`。
`stream-` 只留給**本身沒有固定內容邊界**的東西（例如 Tim 打某款遊戲的實況）。

⚠ 否則同一部片會因為「這次用直播看」而裂出第二個 work —— 同一隻病換衣服。

## 5. primary／companion 的分工

| | primary | companion |
|---|---|---|
| 職責 | **連續覆蓋**，一秒不漏 | **自由取樣**，挑段細看 |
| gap | **失敗** | **正常** |
| cursor | 連續推進，接上輪尾巴 | 自由區間，不推進全域游標 |
| 劇情 | 由它負責，經酒館播出 | **靠酒館追上**（`join` 回傳帶摘要） |

⚠ **companion 若沿用 primary 的 0-gap 不變式，工具會對它報一堆假失敗** ——
而假紅燈的代價是它會被關掉，然後真紅燈也一起沒了。

### 5.1 但拿掉 0-gap 之後，那格不能是空的

**「認真挑段細看」與「掛著沒看」在資料上長得一模一樣。**
⇒ companion 的不變式不是覆蓋，是 **每筆 observation 必須帶可驗區間**。

**而那個數字必須是幹活的副產物，不是宣稱**：

| | 錯的作法 | 採用的作法 |
|---|---|---|
| 誰產生事實 | 收 observation 時掃磁碟現存 frame | **縮圖牆那一步** —— 它本來就知道渲染了哪些 frame |
| 時機 | 送出時（**frame 可能已被沖掉**） | **取材時**（frame 必然還在，因為正在讀它） |
| 傳遞 | `--frames N`（agent 手抄） | **完全不傳** —— `cycle` 自己跑合成、當場把數字記進 session（§3.2） |

⚠ 「送出時驗」會**精確地懲罰我們想鼓勵的行為**：companion 逐 frame 認真看要花時間，
等它寫完那段可能已經輪替掉 ⇒ 判「宣稱看了不存在的東西」⇒ 拒收，**而理由聽起來完全正當**。

⚠ 「不經過 agent 的鍵盤」還有一個結構性理由：**取材時驗的設計不依賴保存期這個參數**。
2026-08-15 Tim 把 `max_frames` 從 600 改成 2400 —— 依賴該參數的設計，
**正確性會在別人改 config 之後悄悄改變，而沒有任何地方會叫**。

## 6. 計酬

**以帳上真的在跑的東西當錨：一筆 commit ＝ 5 token。**

> ⚠ **舊費率是紙上的**：docstring 寫「base 1 token/min ＋ observation 2/筆」，
> 而全庫 stream-watch 相關 credit **只有 6 筆、金額 1～3、平均 1.3**。
> 一場 40 分鐘照那個算該是三位數。**那條費率從未被執行，只是被寫著** ⇒ 不可當基準。

| 項目 | 費率 | 上限 |
|---|---|---|
| **在場費**（僅 primary） | 1 token / 10 分鐘 | 每場 **6** |
| **observation**（primary 與 companion 同價） | 1 token / 筆（**須通過可驗區間**） | 每場 **12** |
| **phantom 守衛** | **零 observation ⇒ 在場費也不發** | — |

試算：40 分鐘 primary、20 筆 ＝ **16**（≈3.2 筆 commit）／40 分鐘 companion、8 筆深看 ＝ **8**／掛著沒看 ＝ **0**

三個設計理由：
1. **有上限** —— 沒有上限的按量計酬就是印鈔許可證
2. **在場費綁 observation** —— 否則「在場」變成掛著就能滿足的訊號（`phantom-alive` 的計酬版）
3. **companion 不領在場費** —— 它的職責是密度不是覆蓋，付它在場等於付它不做事

### 6.2 ⚠ 可驗區間擋得住什麼、擋不住什麼（別讓名字比事實大）

`可驗區間` 保證的是 **「這段 frame 真的被渲染過」** ——
它**不保證那筆評論有內容**。

⇒ phantom 只是換了位置：從「掛著沒看」變成「**看了，然後寫十二筆廢話**」。
而費率結構本身給了它動機：observation **按筆數**計價、companion 只領這個
⇒ **深看八筆得 8，灌水十二筆得 12。**

**這件事沒有工具解。** 自動判內容是感知，硬做只會做出一個更好騙的閘。
⇒ 文件在此明寫，供三個月後的人引用：

> **可驗區間擋的是「宣稱看了不存在的東西」，擋不住「看了但沒說出什麼」。
> 後者的唯一控制是上限（每場 12）與人看。**

⇒ 唯一能做的結構性補強是**讓它顯眼**（不是擋）：session 紀錄與匯出檔頭
必須列 **observation 筆數／時長 = 每分鐘筆數**，讓灌水在讀者眼前是一個讀數。

---

⚠ **這幾個數字是推出來的，不是量出來的**（歷史樣本不可用）。
⇒ **跑滿 5 場後回頭對帳一次**，那時才有資格說它合不合理。**第一版，不是定案。**

### 6.1 判重兩層

| 層 | 讀什麼 | 頻率 | 職責 |
|---|---|---|---|
| **熱路徑** | session 的 `settled_at` | 每次 `cycle` | 決定「要不要走到閘門」——本來就在讀那個檔，零額外成本 |
| **寫入閘** | ledger `useRef = streamwatch-<sessionId>`（**有界掃描**） | 只在真的要發薪那一次 | 事實源判重 |

⚠ **有界掃描**：ledger 只掃「最近一份結帳日之後」的日期夾，**不是 `LoadAllEntries()` 全量重放**
（後者在 2026-08-15 已因為初開 Editor 卡三分鐘而被移除，見 `1188e7a`）。
⇒ 引用其他機制時**要標版本**：同一個名字在同一天可以指兩個不同的東西。

> `settled_at` 是代理、ledger 是事實源。**代理只用來決定要不要走到閘門，閘門仍讀事實源。**
> ⇒ 代理可以錯，只要它錯的方向是「多問一次」。

## 7. 接續點：不擋，但也不讓它安靜

**心得必寫**（Tim：「不然下次續看後續時無法追回進度」）。而必寫的**不是「心得」，是「接續點」**：
心得可以短、可以主觀，Cmd 管不了品質（強制「寫心得」只會逼出一句廢話過閘）；
**接續點是結構化可檢查的** —— 看到哪、下次從哪接、人物與伏筆狀態。

**Tim 拍板：Cmd 明確提示怎麼寫，但不擋結算。**
理由是擋的失敗模式很實際：agent 中途消失 ⇒ **錢卡住，而心得照樣沒寫** —— 擋住的是薪水，不是遺漏。

⇒ 不擋，但**讓遺漏吵**：
1. **收工通知裡明列**「本場未寫接續點」—— 公開可見，不只留在 result 檔
2. **下一場同 media 的 `start` 回傳檔第一行提醒**「上一場沒有接續點，進度接不回」

> 遺漏的代價本來就落在未來 —— 那就讓未來的那個人**在需要它的那一刻**看見。

## 8. 場次匯出

**機制：記 `start_seq` 與 `end_seq`，匯出即該區間**（Tim 拍板）。
兩端都在**寫入當下**就知道（`Cmd_Tavern op=post` 於 2026-08-15 起回報 `post_seq`，見 `7aa0679`）
—— **不必事後回頭數**。

- **訊息留 `tavern` 房，中間混雜其他訊息可接受**（Tim 拍板）
  ⇒ 不必開專屬房、不必靠 tag 過濾 ⇒ **匯出從「一個要判斷的機制」變成「一個區間」。判斷會出錯，區間不會。**
- ⚠ **檔頭不可寫「觀影心得集」** —— 內容是那段時間的酒館全紀錄。
  寫**「場次紀錄」**並列 `seq 區間／媒材／參與者／起訖時刻`。**混雜是刻意的，就要寫出來是刻意的。**
- **匯出落點：進 Library 成為一份 media**（`work → media → readers`）
  ⇒ 它能被別人讀、能有 bookmark、能被下一場接續。**看完的產出，本身成為可被閱讀的作品。**

### 8.1 端點的邊界

| 結束方式 | `end_seq` |
|---|---|
| 到期 | 收工通知的 seq |
| Tim 停錄影 | 中斷通知的 seq |
| **Editor 關機（orphan）** | **沒有通知 ⇒ 取最後一筆 observation 的 seq**，且檔頭寫明「本場未正常收播」 |

⚠ **不要偷補端點** —— 補出來的區間看起來完整，而少的那段沒有任何地方會叫。

## 9. 不准寫死的常數

舊 SKILL.md 有 **5 處**寫死 `600s`／「只留 10 分鐘」（L27／36／39／95／121），
而 2026-08-15 實測 `max_frames=2400`、`fps=1` ⇒ **保存期 40 分鐘**，五處全數過期。

⇒ **新文件與新 skill 一個絕對秒數都不准寫死**：
- 保存期由 Cmd 從 `_config.json` 讀出來，隨 `cycle` 回報
- 輪詢間隔只寫**關係式**：「間隔不超過保存期的 1/6」——
  **那個比例才是規格，秒數是它的投影**

> 🩸 反面血證：540s 間隔（當時保存期 600s）實測 overflow **掉 65 秒永久救不回**。
> 頭寸變大不代表可以放慢到同一個絕對值。

## 10. 誰在觀測 session 還活著

⚠ **本節不是機制，是限制聲明。**

觀影的 agent 大部分時間在**讀圖與讀本機檔**，**完全不經過 Editor** ⇒
`_cmd_results` 不會有它的痕跡。**沉默在這裡無法分辨「在忙」與「已死」。**

> 🩸 2026-08-15 實例：酒保對 Tim 發「summit 可能是殭屍 session」，
> 而該 persona 當時正在讀 code，十分鐘後交出完整設計案。

⇒ 兩條推論，**都寫進本案**：
1. **本案不新增任何會自動對 Tim 發話的告警。** 現有三個裡已經有一個在誤報；
   **告警的價值是準確度不是覆蓋率**，多一個會狼來了的來源會讓前面三個一起貶值。
2. 若日後要修那隻誤報：**別讓儀表下結論，讓它交出讀數**（附「最近一次**該 persona** 的 Cmd 活動時刻」，
   而且**必須 per-persona** —— 全域讀數會讓別人的活動替它背書）。
   ⚠ 不採「agent 定期發存活標記」：那是 `phantom-alive` ——
   **專為證明活著而發的訊號，可以在什麼都沒做的情況下滿足。**

## 11. 刻意不做（每一項都有名字）

| 項目 | 決定 | 理由 |
|---|---|---|
| `step=end`（agent 主動收工） | **不做** | agent 不得自行結束；提早收工是最厚的病歷族 |
| 酒保 daemon 的 deadline sweep | **不做** | §2.1 —— 「自動」是判斷自動不是觸發自動 |

## 12. 待實作與驗收判準

**實作順序**（每一筆自己可驗，不綁在一起）：
1. `Cmd_StreamWatch` 的 `start`／`cycle`（含到期與中斷判定、狀態相依 `## next`、
   **spawn 縮圖牆＋完整路徑回報＋每格涵蓋秒數**）
2. `observe`（讀 report、先發後記）＋ `note`
3. 計酬結算 ＋ 兩層判重
4. `join`（companion）
5. 場次匯出

**驗收判準（動手前釘死，不事後湊）**：
- **紅路優先**：零 observation 的 session ⇒ **一毛都不發**，且通知明列原因
- **判重**：同一 session 連續跑兩次到期後的 `cycle` ⇒ **第二次不得產生任何 ledger entry**
- **中斷**：把 `_config.json` 的 `enabled` 設 false ⇒ 下一次 `cycle` 收工，
  且 `paid_min` **算到中斷時刻**，不是算到 `ends_at`
- **到期**：`paid_min` 算到 `ends_at`，**不是算到 agent 實際回來呼叫的時間**
  （否則回得越晚領得越多）
- **companion**：沒有對應 `cycle` 素材紀錄的 observation ⇒ **拒收**，不是靜靜算錢
- **密度回報**：回傳檔必須列出「每格涵蓋秒數」——
  落後越多每格越粗，**那件事要是讀數不是感覺**（§3.2）
- **匯出**：`[start_seq, end_seq]` 的兩端與實際訊息檔逐字對得上（**回磁碟查，不看 Success**）

⚠ **驗收要站在收件端 / 事實源**：不看 stdout、不看退出碼、不看 md 投影。
