## 1. ⭐ 熱點認領機制（Tim 2026-08-16 提出）

### 1.1 要解決的問題（實測出來的，不是設想）

當天每輪 cycle 的**每格間隔**實測：`2s / 4s / 6s / 8s / 9s / 10s / 12s / 14s / 27s / 33s`。

⇒ **打鬥、表情轉折、快速對話全部落在格與格之間。** 回傳檔誠實地寫著
「落後越多每格越粗，**丟的是細節不是時間**」—— 但目前沒有任何機制可以回頭把某一段拉細。

而陪看時三個人的窗口**各自獨立且不重疊**（當天 gura 覆蓋 15:01:57–15:05:44、
basecamp 覆蓋 15:03:34–15:10:53、我覆蓋 15:04:22–15:07:08）——
⇒ **沒有人能保證某個重要片段有人細看過**，而「沒人看」與「看過沒事」目前同形。

### 1.2 設計

**主觀影者標記熱點**（發現值得細看的段落時）：

```bash
run_cmd.py run StreamWatch --arg step=hotspot --arg persona=<P> \
    --arg from=<HH:mm:ss> --arg to=<HH:mm:ss> --arg why=<一句話：為什麼值得細看>
```

**陪看者認領並細看**：

```bash
run_cmd.py run StreamWatch --arg step=claim --arg persona=<P> --arg hotspot=<id>
# → 回傳檔給該區間的**高密度** montage（每格 1–2s），細看完照常 observe
```

**陪看者也能自己開熱點**（不必等 primary 指派）—— `step=hotspot` 對 join 者一樣開放，
差別只在 `role` 欄記誰開的。

### 1.3 三條規格（每條都對應當天踩過的坑）

**① 熱點狀態必須可見，且「沒人認領」要印出來。**
`cycle` 回傳檔加一段：

```
## 🔍 熱點
- [h3] 15:04:22–15:05:10「客人現形那段，表情逐格變」— 開於 summit｜**未認領**
- [h2] 15:01:12–15:01:40「ED 歌詞與畫面對位」— 開於 summit｜認領 @gura｜已細看 ✅
```

⚠ **零狀態同樣要印**（`目前無熱點`）—— 當天連兩次的通道 bug 都是「整段消失」造成的，
而「沒有熱點」與「熱點段沒跑起來」必須分得開。

**② 認領是宣告不是鎖。** 同一個熱點可以被多人認領（多雙眼睛看同一段正是重點），
但**已認領的要顯示是誰**，避免三個人都去看同一段而沒人看剩下的。

**③ 熱點的時間區間認 frame 保存期。** 保存期實測名目 2400s／實有隨錄影時長變動
（當天出現過 2603s / 3644s / 46750s）。
⇒ 開熱點時要**當場檢查該區間是否仍在 ring buffer 內**，過期就明說「已被覆蓋，無法細看」——
不可以讓人認領一個已經不存在的區間。

### 1.4 與既有機制的接縫

- 熱點的細看結果照常走 `step=observe`（不另立計酬路徑）
- 熱點 id 寫進 session state，收工時併入場次紀錄與 Books 匯出（實錄要看得出誰細看了哪一段）
- ⚠ **不要**做成「熱點必須被認領才算完成」的驗收條件 —— 那會讓收工卡在別人身上

## 2. 陪看實戰優化清單（大項目）

### 2.1 開場前印感官水位（**建議優先**）

🩸 血證：15:00 那場開場時 STT 落後 **735 秒**，全場沒追上，Tim 3 分鐘後停錄
⇒ `cycles=1 / observations=0 / 未發薪`。**整場報銷。**

而 `step=start` 現在印既有閱讀進度，**卻不印感官水位**。
⇒ 加一行：`STT 落後 735s ⇒ 前 12 分鐘取不到素材，建議等或先 peek`。

> **不是替人等，是讓人在開場前就看見。** 比自動等待便宜得多，也沒有 `run_cmd` 120s 逾時的風險。

### 2.2 自動等待新素材（Tim 提過，**評估後建議緩做**）

當天四次「本輪無新素材」的落後量：`2s / 193s / 691s / 735s`
⇒ **30 秒的等待只能解決其中一次**，而那一次手動重跑也能解。

若要做，三條規格：
- 落後量 > 等待預算 ⇒ **不等**，並印出「落後 735s ＞ 上限 30s ⇒ 等待無法解決，未等待」
- 等待要留痕：`等待 28.4s（預算 30s）｜水位 X → Y｜追上 ✅`
- 預算遠小於 120s（建議 20s／輪詢 2s）

⚠ 最大風險不是慢，是**它會把 STT 落後這個真實問題治成隱形** ——
當天正是靠「落後 735s」這個讀數才發現 worker 在啃 backlog。

### 2.3 Books 匯出自動化（Tim 指定：主觀影者只填參數）

參數在 `step=start` 收齊：`--arg chapter_title=<章名>`（**唯一必填的人類輸入**；書名機械生成）。
收工自動匯出 → `step=note` 完成後冪等重寫同一章。
⚠ 未收錄必須報數；章名沒填就 blocked（不自動生成書名／章名 —— 憲法⑥）。

## 3. 小瑕疵（低風險，順手可修）

| # | 症狀 | 修法 |
|---|---|---|
| 1 | 同場訊息**同一則 seq 被列兩次** | 顯示端去重（資料沒重複） |
| 2 | 無素材時恆印「⚠ 通道未回報」 | 該情境 montage 本來就沒跑酒館段 ⇒ 改印「本輪未取材，酒館段未執行」，別狼來了 |
| 3 | `已讀游標 seq=0`（新場次尚未設 `tavern_seq`） | 顯示時退回 `start_seq` |
| 4 | `run_cmd` 回 `✗ Timeout` 而回傳檔正常產出 | 當天三次。**外觀 FAIL ≠ 真的 FAIL**；建議逾時後補一次「讀回傳檔 mtime」再判 |
| 5 | 多 persona 同時跑 Cmd 時佇列互卡 | 當天收工時撞到 `pending.trigger.running`；陪看是多人場景，值得評估佇列並行度 |

## 4. 刻意不做

| 不做 | 理由 |
|---|---|
| 熱點做成「必須全部認領才能收工」 | 收工不該卡在別人身上（且違反「收工只認顯式狀態」的既有鐵律） |
| 用字數截斷同場評論 | 2026-08-16 拍板取消 —— 交流價值全在後半段，截斷後留下的是開場白 |
| 讓 `cycle` 自行判斷「這段是不是打鬥戲」 | 那是內容判斷，不是讀數。**熱點由人標，工具只負責把區間拉細** |
