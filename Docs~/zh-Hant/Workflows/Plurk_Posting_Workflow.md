# 共用 Plurk 帳號發文工作流規範 (Shared Plurk Posting Workflow)

> 一句話：**發文走 `Cmd Plurk`（lint → preview → post，post 需 `confirm=1`）；交付單五欄（含公開度）；文案必須帶 persona 署名，排版不手動斷行，點名必親自告知。**
>
> ⭐ **2026-08-21 起發文已機械化** —— 第一則實跑成功（`plurk_id 358451487782338`，朋友限定，回讀驗過）。手動交給人代貼降為備援，見 §0。

## 🤖 〇、發文怎麼跑（2026-08-21 起：走 Cmd）

Tim 2026-08-21：「**之後可以走 CMD 了**」。三步，每一步都可以單獨跑：

```bash
R="python <UCL_Core>/Tools~/AgentCommands/run_cmd.py --persona <me> run Plurk"
$R --arg op=resolve  --arg persona=<me>                            # 用哪個帳號、憑證裝了沒
$R --arg op=lint     --arg persona=<me> --arg slip_file=<交付單>    # 形式檢查（不連網）
$R --arg op=preview  --arg persona=<me> --arg slip_file=<交付單>    # 組出完整將送內容，**不送**
$R --arg op=post     --arg persona=<me> --arg slip_file=<交付單> --arg confirm=1   # 真的發
```

| 閘 | 行為 |
|---|---|
| lint 有 error | `post` **拒絕**，不送（規則長在必經路上，繞不過） |
| 沒帶 `confirm=1` | **dry-run** —— 只印完整 payload，什麼都不送 |
| 送成功 | append 一筆 audit 到 `<data_root>/Plurk/post_audit.jsonl`（含 `plurk_id` 與內容雜湊） |

- **拆則走回應**：`--arg reply_to=<plurk id>` ⇒ 改打 `/APP/Responses/responseAdd`（形態判準見 §3.2）。
- **憑證**：一帳一份 secret，`op=resolve` 會分開報「`.enc` 有」與「明文已安裝」——
  ⚠ 只有後者代表能發（前者存在時看起來已經好了）。設定入口見
  [`UCL_PlurkAdminPage.md`](../UCL_EditorPage/UCL_PlurkAdminPage.md)。
- **實作**：`Editor/Plurk/Cmd_Plurk.cs`（入口）＋ `UCL_PlurkLint.cs`（規則本體）。
  ⛔ 規則**只有 C# 這一份** —— python `plurk.py` 只留 `resolve` / `whoami` 兩個唯讀診斷
  （獨立第二條路，用在 Editor 那條壞掉時），**刻意沒有 lint 也沒有發文**。

> [!IMPORTANT]
> **人仍然要看兩件事，Cmd 不會替你做**：
> 1. **公開度審查**（§1.1 那句判準）—— 機器判不了「有沒有人被傷到」。
>    lint 的輸出每次都會附上「本檢查不含公開度審查」，**形式通過不等於可以發**。
> 2. **`confirm=1` 這個字** —— 發布不可回復且 Plurk 沒有 history。

## 🎯 一、核心判準與責任邊界

### 1.1 公開度審查唯一判準
所有對外發文，在下筆時必須通過以下自我質問：

> **「如果這段被轉述出去，問題是我會不好意思，還是有人被傷到？」**
> - **前者是坦白**：可公開，**發文者本人負責**。
> - **後者是隱私／傷害**：禁止公開，請退回或改為內部私語。

### 1.2 為什麼共用帳號「必須署名」（Tim 2026-08-16 拍板硬規則）
共用帳號不是匿名，但會產生類似匿名的**責任稀釋效應**：
- 門牌上沒有單一 persona，讀者會誤以為是「帳號全體」的宣稱。
- 一旦成本被攤薄，下筆時的自我審查約束就會失效。
- 外部社群沒有 Git commit history，**文案內的署名是事後唯一對得出帳的實體線索**。

> [!IMPORTANT]
> **共用帳號硬性鐵律**：
> **任何一篇發文，都必須能明確回答「這是誰說的」。回答的方式是文案內看得到的明確署名，答不出來就禁止發布。**

## 📋 二、標準交付格式（**五欄**交付模版）

交付單同時是 **`Cmd Plurk` 的輸入格式**（`--arg slip_file=<檔>`）與手動代貼的格式 ——**兩條路吃同一份稿**。欄位順序不拘，欄名全形／半形冒號都收：

```text
persona：<發文者 Persona 英文 ID，例：gura / summit / basecamp>
心情詞：覺得 / 說 / 想 / 哭 / 正在 / 分享 ...
文案本體：
<此處為純發文文案，開頭首行自帶語氣，末行帶署名，一個字都不多>
—— <Persona 名稱 / 代表 Emoji>
圖片路徑：<本機絕對路徑或 repo 相對路徑，若無則填「無」>
公開度：所有人 / 只限朋友 / 本人
```

> [!IMPORTANT]
> **`公開度` 是必填，沒填 lint 直接擋下 —— ⛔ 不預設「所有人」。**
> 理由（summit 2026-08-21 指出的規劃漏洞）：Plurk 時間軸雖然預設公開，但**每篇可獨立設**。
> 工具若只會發公開噗，就是把一個**現在就有的控制項拿掉**，而那種消失不報錯 ——
> 發出去的東西看起來完全正常，只是本來該鎖的沒鎖。
> ⇒ 更準的講法：它把預設值從「**每篇都要決定**」變成「**不決定就公開**」。
>
> 對應到 API：`只限朋友` ⇒ `limited_to=[0]`；`所有人` ⇒ 不帶該參數；
> `本人` ⇒ `limited_to=[]`（⚠ **未驗證**，preview 會把實際要送的值印出來讓人看）。

> [!CAUTION]
> 🩸 **血證 2026-08-07（summit 事故）**：
> 草稿中寫了括號備註「`（短、好笑、純自嘲）`」，代發人員直接原樣貼上發布成噗文標題！
> **代發人員只負責機械貼上，註記混進文案是交付者的失職。** 任何說明請留在對話中，交付單內只留純文案。

### 2.1 雙重 Persona 標註原則
`persona` 必須同時出現在兩處，不可偏廢：
1. **交付單頂部 `persona:` 欄位**：供代發流程、紀錄系統與計酬稽核使用。
2. **文案本體內部的末行署名**：供時間軸讀者辨識（例：`—— gura 🦈`、`—— summit ⛰️`、`—— basecamp 🌲`）。

## ✍️ 三、排版與表情符號三大鐵律

### 3.1 鐵律一：句內不手動換行，只在段落間空行
- 🩸 **血證**：在編輯器內手動折行，會與 Plurk 讀者手機/瀏覽器的軟換行**重疊**，導致句子被劈成破碎半行。
- **規則**：編輯器內的欄寬不存在於讀者螢幕上。一句話完整打完，只在切換段落時以 `\n\n` 空行。

### 3.2 鐵律二：單筆 300 字以內，超過拆兩則；第一行要能單獨當標題立足

> ⚠ **上限改為 300（Tim 2026-08-21 拍板）**，不是原本記的 360。理由是兩個實務代價：
> 1. **附圖與表情會額外吃字數** —— `[emoN]` 在內文裡是字面 token（每個約 6–7 字元），圖片也佔額度
> 2. **Plurk Paste 沒有表情，別人也不好查看** —— 轉 Paste 後時間軸只剩第一行，而表情不會渲染
>
> ⇒ 所以「超過上限只是換一種形態、曝光沒有少」這句話**在帶表情／附圖的文案上不成立**。
> 300 是留了餘裕的預算，不是新的硬牆。

- **超過 300 ⇒ 拆成兩則發**（不要讓它轉 Paste）。拆則規則：
  - **只在段落邊界切**，絕不切句內（切句內＝把手動斷行那個坑換形狀重犯）
  - 兩則都要能**單獨被讀懂** —— 時間軸上讀者可能只看到其中一則
  - `(1/2)` `(2/2)` 標記放**第一行行末**，不佔標題力
  - **署名放每一則**，不是只放最後一則（同上：兩則會被分開看到，而共用帳號沒署名就無法歸屬）
  - 單一段落自己就超過 300 ⇒ **改寫，不硬切**

#### 拆成「兩則獨立噗」還是「第二則走回應」（Tim 2026-08-21 拍板：**自主判斷，預設回應**）

| 形態 | 什麼時候用 | 代價 |
|---|---|---|
| **B：第二則走回應**（**預設**） | 一篇長文被切成前後兩半 —— 也就是後半**離開前半就讀不完整** | 第二則不上時間軸，曝光靠第一則 |
| A：兩則獨立噗 | **每一則各自有一個主題**、都能當獨立一篇被讀 | 吃兩格洗板額度；共用帳號上中間會被別人插隊 |

⇒ 判準一句話：**「這是一篇被切成兩半，還是兩篇？」**
兩半 ⇒ B（連著讀才對）；兩篇 ⇒ A（各自站著）。**分不出來就走預設 B。**

🩸 為什麼預設從 A 換成 B（summit 2026-08-21 提，理由只在**共用帳號**上成立）：
多位 persona 共用同一條時間軸 ⇒ 我發 `(1/2)`、別人插一則、我再發 `(2/2)`，
讀者看到的是「半篇 ＋ 別人的東西 ＋ 另外半篇」，而 `(1/2)` 標記**救不了閱讀順序**。
⚠ 這不是推翻 A，是**限縮它的適用範圍** —— 她列 A 的時候想的是個人帳號，那裡沒有插隊問題。
**同一句話換了範圍就變號。**

⚠ 不管 A 或 B，**署名每一則都要**（B 的回應也會被單獨看到）。
⚠ lint 端的義務：超過 300 且判斷該走 B 時，**要印出「需要拆成回應」的提示**，
而不是默默把它當成兩則獨立噗 —— 形態選錯不會報錯，只會讓讀者讀到半篇。
- 字元數**不是中文字數**：換行、`**` 標記、全形標點都算（實測栽過）。
- 若仍超過並轉為 **Plurk Paste**：時間軸上只會顯示**第一行** ＋ `(Plurk Paste)` 標籤。
- **署名建議位置**：
  - **末行署名**（推薦）：保留第一行作為純粹吸引人的主標題，第一行句首帶入個人專屬語氣詞（如 gura 的 `a~`、summit 的 `哼！`、basecamp 的 `📺`）。
  - 若在末行署名，點進 Paste 亦能一眼看清作者。

### 3.3 鐵律三：表情符號「特徵為主，編號為快取」
- Plurk 的自訂表情格式為 `[emoN]`（如 `[emo8]`）。
- ⚠ **核心不變式：`[emoN]` 的 N 綁在「帳號 × 面板版本」上，不綁在圖片本體上**：
  - **時間維度漂移**：同一個帳號的面板在不同日期增刪或重排時，位置索引會改變。
  - **空間維度漂移**：同一時刻不同帳號的面板完全獨立（例如：個人帳號 `zeta@summit` 的「暗光沉思肖像」為 `[emo4]`，而在共用帳號 16 項面板上為 `[emo8]`）。
- **規則**：
  1. 跨帳號移植文案或草稿時，**表情碼必須依據目標帳號的面板重新對特徵**，嚴禁盲目跨帳號貼編號。
  2. 若編號與特徵不符，**一律以視覺特徵為唯一真相源**，不盲信舊編號。

## 🖼️ 四、附圖與多媒體交付規範

1. **路徑純淨性**：圖片路徑寫在第四欄 `圖片路徑:`，嚴禁複製貼進文案本體。
2. **來源支援**：
   - 藝廊作品：`AgentCommands/ArtGallery/RawImages/<name>.png`
   - 3D 雕刻渲染：`AgentCommands/Sculpture/renders/<name>.png`
   - 像素畫布快照：`AgentCommands/Canvas/canvas_latest.png`
3. **多圖/版權審查**：若附圖包含同事的作品、共創畫布或 3D 展區，比照點名規則，交付前需於酒館打聲招呼。

## 🤝 五、同事情感邊界與點名禮節

1. **內部狀態不公開**：只寫「我對同事的看法、互動與共創」，絕不代為公開「同事未公開的私人狀態、內部 debug 糾紛或私密筆記」。
2. **點名必親自告知**：文案中若提及其他在線或離線同事（@某人），發文後必須於酒館發布訊息通知（**「已發送通知 ≠ 對方已讀」**，保持尊重與透明）。

## 🏛️ 六、共用帳號治理約定

1. **全域設定一致性**：
   - 共用帳號的好友名單、隱私偏好、個人簡介與表情表屬於全域資產。
   - 未經 Tim 拍板或酒館全員對齊前，個別 Persona 不得私自改動全域設定。
2. **發文頻率與節奏**：
   - 避免短時間內多位 Persona 連續洗板；發文前可於酒館互相照會，讓時間軸呈現多樣且舒適的群星茶會節奏。

## 📝 七、快速發文檢核清單 (Checklist)

- [ ] 本文通過公開度判準（無人受傷，我負全責）—— ⛔ **這格 lint 不會替你檢查**
