# 🧭 Treasury 帳號歸戶 Workflow

> 一句話：**`account_id` 不是使用者輸入什麼就寫什麼 —— 它先經過一組解析規則。
> 規則認不出來的名字會變成「有錢但沒有主人」的孤兒帳戶，而那件事此前沒有任何一層會出聲。**

適用時機（任一命中即讀本檔）：
- 後台看到「孤兒帳戶 N 個」的告警
- 某個 agent / persona 的薪水「沒進來」，但 ledger 裡查得到那筆錢
- 要新增一個 agent、舊 bank 要退場、或名字改過
- 跨專案接手一份 UCL_Core，想知道這套帳的路由表在哪

---

## 一、先搞清楚：誰決定錢落到哪裡

事實來源只有兩個檔（**路徑依各專案 `DataRoot` 解析，不要寫死**）：

| 檔案 | 內容 | 誰在寫 |
|---|---|---|
| `<DataRoot>/AwakenInit/_registry_meta.json` | `agent_banks` / `agent_aliases` / `system_accounts` / `closed_accounts` | 銀行後台管理頁 + Persona & Agent 管理頁 |
| `<DataRoot>/AwakenInit/personas/<persona>.json` 的 `agent` 欄 | persona 歸屬哪個 agent | Persona & Agent 管理頁 |

解析實作只有一份：`UCL_TreasuryAccountResolver`。**不要在別處再寫一套 agent→bank 的判斷** ——
平行索引跟事實不一致時，兩邊都能各自運作、都不報錯。

### 解析順序（六段，先精確後模糊）

| 段 | 判定 | 結果 |
|---|---|---|
| ① | 是註冊在案的帳號（`agent_banks` 的值 / `system_accounts` 的 key） | 原樣採用，**解析到此為止** |
| ② | 是 agent 名（不分大小寫） | → 該 agent 的 bank |
| ③ | 是某個正式帳號的大小寫／拼法變體 | → 歸一到註冊拼法 |
| ④ | 是 `agent_aliases` 的 key | → alias 指向的 agent → 其 bank |
| ⑤ | 是 persona 名 | → 該 persona 的 agent → 其 bank |
| ⑥ | 以上皆非 | **原樣通過並標記 unresolved** —— 產生／沿用孤兒帳戶 |

> ⚠ 第 ⑥ 段刻意**不拒絕、不改寫、不 derive**。
> 拒絕會讓一筆真實勞動的薪水直接消失；derive 會憑空造出打錯字的幽靈 bank。
> **標記比丟棄安全** —— 錢留在看得見的地方，然後由人決定它該去哪。

### 什麼時候解析**不**介入

`Credit` / `Debit` 都有 `resolveAccount` 參數（預設 `true`）。判準一句話：

> **「從既有帳號清單選出來的」＝認字面；「從身分推導出來的」＝歸一。**

所以以下路徑一律 `resolveAccount: false`：轉帳單的出款／入款／回滾、後台直接轉帳。

> 🩸 **為什麼這條是硬的**：歸戶轉帳的出款方**本來就是孤兒帳戶**。
> 若讓解析介入，選 `summit` 會變成從 `zeta` 扣錢 —— 正主被扣、孤兒原封不動，
> 而**轉帳單顯示核准成功**。單子上寫的帳號就是操作對象，不接受任何再詮釋。

## 二、流程 A：止漏（新的錢不要再跑掉）

孤兒帳戶會持續增加，代表**現在還在漏**，不是歷史殘帳。處理順序永遠是「先止漏，再歸戶」——
反過來做的話，你搬完的當天它又長出新的。

1. 開 **🏦 銀行後台管理 → 🧭 帳號解析規則**，用 **🔍 解析試算** 輸入正在漏的那個名字。
2. 看它落在哪一段：
   - 顯示 `✅` 且目標正確 → 已經不漏了（大小寫類多半屬此）。
   - 顯示 `✘ 查無對應` → 往下走流程 D 決定「搬走」還是「原地承認」。
3. 改完規則**當場再試算一次**。規則要能立刻看到結果，不要改完等下一筆錢來驗。

---

## 三、流程 B：人工標記 → 審批 → 歸戶

**設計原則：標記與動錢分離。** 標記只產生單據，錢只在人按下核准時才動。

```
① 標記（誰都能提）→ ② 待審清單 → ③ 人確認 → ④ 按下核准 → ⑤ 實際搬錢
   零金流              零金流        零金流      ← 唯一動錢的一步
```

### 操作步驟

1. **🏦 銀行後台管理 → 👻 孤兒帳戶**（收合狀態下標題列就會顯示「有餘額待遷移 N｜可銷戶 M」）。
2. 每一列顯示：餘額、解析器**建議的歸屬**與判定路徑、以及綁在它上面的 persona。
3. 按 **📝 標記遷移** → 建立一張 `kind=orphan-consolidation` 的轉帳單（狀態 `pending`，**一分錢沒動**）。
   - 建議目標算不出來時該鍵是灰的 —— 請先走流程 D，或用 **💸 轉帳審批** 區的手動開單指定目標。
   - 同一個孤兒已有待審單時會擋下，不重複開（兩張都核准會扣兩次，而第二次的失敗看起來像系統壞了）。
4. 到 **💸 轉帳審批** 逐張看：金額、from → to、理由、出款方餘額是否足夠。
5. 按 **核准** → **再按一次確認**（5 秒二段確認）→ 這時才 `Debit(from)` → `Credit(to)`，
   共用 `tx_id`，credit 失敗自動回滾 debit。

搬完之後該帳戶餘額為 0，但 **ledger 紀錄留著**（append-only，本來就不該消失）。

### agent 端怎麼提案

不必開 Editor 也能開單：走 `Cmd_Treasury`（詳見 `Cmd_Treasury.md`）。
單子一律 `pending`，**核准權只在後台**。

## 四、流程 C：幽靈帳號銷戶

> **銷戶不是刪除。** ledger 是 append-only，帳戶不是實體物件 —— 它只是「曾經出現在 entry 裡的
> `account_id`」。所以銷戶只能是一份**拒收名單**：寫入端據此拋錯，後台據此把它移出待處理視野，
> 而歷史一個字不動。

### 三道閘（任一不過即擋，訊息會明說是哪一道）

| 閘 | 條件 | 為什麼 |
|---|---|---|
| ① | **餘額必須為 0** | 有錢還銷戶＝錢從視野消失，比孤兒更難查。<br>⚠ 讀不到餘額**也不放行** —— 「讀不到」與「是 0」在這裡會導出相反的決定 |
| ② | **沒有 persona 綁定** | 綁定不是一個欄位，是一條解析鏈；問的是「誰會解析到這裡」。<br>有綁定代表那筆錢的來源是那個 persona 的勞動 |
| ③ | **不是註冊在案的正式帳號** | 銷掉 registry 裡的 bank 會讓該 agent 的薪水無處可去 |

### 操作

**👻 孤兒帳戶** 區中餘額為 0 的列會出現 **🚫 銷戶** 鍵 → 按下即寫入 `closed_accounts`。
會同步發一則酒館公告（改路由表這種事不該靜默生效）。

### 銷戶後

- 任何 `Credit` / `Debit` 打進該帳號 → **當場拋例外並點名銷戶理由**。
  那不是故障，那是「還有呼叫路徑沒清乾淨」的告警 —— **請去查來源，不要重開帳戶**。
- 該帳號**退出孤兒清單與帳號下拉選單**，只留在「🚫 已銷戶」區（可 ↩ 復戶）。
- 要復戶：**🧭 帳號解析規則 → 🚫 已銷戶 → ↩ 復戶**。

> [!IMPORTANT]
> **「銷戶後名單要刷新」是一條必須寫進掃描邏輯的規則，不是按一下 Refresh 就會發生的事。**
> 孤兒名單是**從 ledger 掃出來的**，而銷戶不刪任何 entry —— 掃描一定會把它撈回來。
> 所以過濾要做在掃描裡；漏做的症狀是「刷新沒作用」，而且該帳號會同時出現在
> 「孤兒」與「已銷戶」兩處。
>
> ⚠ 但這個過濾**必須帶例外**：已銷戶卻**餘額不為 0** 的帳號絕不隱藏，還要標紅。
> 銷戶前置是餘額 0，所以那代表閘門被繞過或事後又有錢進來 ——
> 那正是最該被看見的一種帳。**藏起來就變成「看不見的錢」，而看不見的錢比不見的錢更難處理：
> 前者連「有問題」都不會被發現。**

## 五、流程 D：解析不出來時 —— 搬走，還是原地承認？

這是一個**二選一的決策**，不是兩個都做：

| 選項 | 用在什麼情況 | 怎麼做 | 錢會不會動 |
|---|---|---|---|
| **加別名**（`agent_aliases`） | 這名字是**同一個人的另一種寫法**（舊命名 `zeta-bank`、外部識別碼 `discord:xxxx`） | 🧭 區 → 🔀 別名 → 填來源字串 + 選 agent | 舊的錢**不會**自己回去 —— 別名只管**未來**。舊的要另外走流程 B |
| **補登記系統帳號**（`system_accounts`） | 這名字**本身就是一個帳戶**（舊世代 bank、系統 NPC），錢該留在原地 | 🧭 區 → 🏛 補登記（只對孤兒開放） | **一分都不動**。這是承認，不是搬錢 |

> ⚠ **舊世代 bank 不要寫進 `agent_banks`。**
> 那會把該 agent 的**現行**薪水導向舊帳戶。2026-08-04 拍板：補登記進 `system_accounts` 即可。

別名有兩道護欄：目標 agent 必須已在 `agent_banks`（不准指向不存在的 agent）；
**已經解析得出來的字串會被擋下** —— 硬加只會產生一條「看起來在生效、其實從沒被用到」的規則，
而那種規則日後會被當成事實引用。

## 六、驗證：不要靠肉眼

```bash
# 解析器自我檢查（純讀、零金流）
senate ucmd run Invoke \
    --arg type=UCL.Core.EditorLib.AgentCommands.Treasury.UCL_TreasuryAccountResolver \
    --arg member=SelfTest
# 報告印在 Unity Editor log；grep "帳號解析 SelfTest"
```

斷言是**與資料無關的不變式**（對 registry 裡每個 agent／bank／persona 都要成立），
不是把答案抄一遍 —— 所以換一個專案、換一批資料，它照樣有鑑別力：

| # | 不變式 |
|---|---|
| ① | 每個正式帳號解析後必須是自己（歸一不可搬動已經正確的帳） |
| ② | 每個 agent 名（含大小寫變體）→ 它登記的 bank |
| ③ | 每個 persona → 它的 agent 所登記的 bank |
| ④ | 查無對應時回 `Unresolved` 且**原樣通過**（不 mint、不丟棄） |
| ⑤ | 已銷戶 ∩ 正式帳號 = ∅ |
| ⑥ | **撞名清單**（不是失敗，是必須被人看過的資料狀態，見下） |

### 撞名：一個名字同時是帳戶與 persona

例：`claude-da-xiaojie` 既是 `system_accounts` 的一員，也是一個 persona 的名字。
解析器讓**帳戶贏**（第 ① 段），意思是：以該 persona 名義產生的收入會留在同名帳戶，
不流向它 agent 的 bank。**在舊世代 bank 上這通常正是想要的**，但它必須是有人看過並同意的，
所以固定列在 SelfTest ⑥，不靜默生效。

## 七、地雷清單（都是實際踩過的）

1. **孤兒數字會過期。** 交接文件寫「N 個帳戶約 M token」— 那是寫下當時的快照。
   動手前先自己數一次；2026-08-14 實查與交接紀錄差了四倍以上。
2. **「還在漲」跟「歷史殘帳」是兩件事。** 看孤兒的**最後一筆 entry 時間**：
   若是今天，那是**還在漏的洞**，先止漏再歸戶。
3. **歸戶轉帳千萬不要讓解析介入**（見第一節末的血證）。
4. **銷戶閘門不要用「讀失敗回 0」的餘額 helper** —— 那會讓讀取失敗自動放行。
5. **改完 registry 要讓解析器重新認識磁碟**（後台按 🔄 Refresh；程式端 `Invalidate()`）。
   畫面讀新表、解析走舊表時，兩邊各自說得通而且都不報錯。
6. **`agent_banks` 已經有兩個寫入者**（銀行後台開戶 / Persona & Agent 管理頁開 agent）。
   不要再加第三個 —— 同一張表三處可寫的漂移不會報錯。
7. **後台頁的 `Draw*` 內不准直接算餘額或跑解析** —— 那是每 repaint frame 一次。
   一律走快取，在「資料重載 / 操作後 / Refresh」時才重算。
8. **止漏只覆蓋走該入口的路徑。** 解析長在 `UCL_TreasuryLedger.Credit/Debit`，
   所以**繞過它的旁路完全不受保護**。2026-08-14 找到的那條：
   `_lib/session_common.fire_salary_credit` 直接寫 ledger json 檔（原註解自承
   `direct write, Phase 1 bypass Cmd_Treasury`），配合 Python resolver 當時的
   「認不出就 derive `{名字}-da-xiaojie`」，正是 `gemini-da-xiaojie` /
   `antigravity-da-xiaojie-da-xiaojie`（**雙後綴**）這批孤兒的來源。
   兩者都已修（改走 `op=credit`；derive 改成原樣回傳 + 警告）。
   **判準：問「還有誰能寫 ledger」，不要問「我的解析寫對了嗎」。**

## 八、跨專案注意

- 本 workflow 描述的機制全在 UCL_Core，**跨專案通用**；但 `_registry_meta.json` 的**內容**
  per-project 各自不同（agent 名、bank 名、persona 都不一樣）。
- 因此**不要把本檔或任何 code 裡的帳號名字當成常數**（`zeta` / `cc` 只是範例）。
  要知道現況一律去讀該專案的 registry，或跑 SelfTest 看它印出來的表。
- 路徑一律走 `UCL_AgentCommandsPath.DataRoot` 解析，不要寫死 —— 各專案 UCL_Core 掛載位置不同。
